Foundations

Dio API client

Generate typed HTTP helpers, API configuration, bearer-token interception, Dio exception mapping, cancellation support, and Riverpod provider wiring.

Generate the preset

kite --api:dio

Canonical forms:

kite api dio
kite --api dio

Generated structure

lib/core/network/ ├── api_config.dart ├── api_endpoints.dart ├── api_exception.dart ├── auth_token_store.dart └── dio/ ├── bearer_token_interceptor.dart ├── dio_api_client.dart ├── dio_exception_mapper.dart └── dio_providers.dart

Automatic requirements

The Dio template declares shared dependencies:

{
  "id": "api.dio",
  "requires": ["api.core", "state.riverpod"]
}

Kite adds the shared API contracts and Riverpod foundation before the Dio-specific files, while deduplicating targets already present in the same generation plan.

Configure the base URL

buildProviderScope(
  overrides: <Override>[
    apiConfigProvider.overrideWithValue(
      const ApiConfig(
        baseUrl: 'https://api.example.com',
      ),
    ),
  ],
  child: const App(),
);

Make a typed request

final client = ref.read(dioApiClientProvider);

final profile = await client.get<ProfileDto>(
  path: ApiEndpoints.profile,
  decoder: (data) => ProfileDto.fromJson(
    Map<String, Object?>.from(
      data! as Map<Object?, Object?>,
    ),
  ),
);

Token integration

Implement the generated AuthTokenStore contract using your secure-storage or authentication module. The bearer interceptor reads the current token and attaches it to outgoing requests without coupling the network foundation to a specific auth implementation.

Failure handling

Dio failures are mapped into an application-owned ApiException representation, covering cancellation, timeouts, connectivity, invalid responses, and unknown failures. This prevents presentation layers from depending directly on Dio exception types.

!
Base URL is intentionally required

The generated config provider should be overridden by the application. Failing early is safer than silently shipping a placeholder endpoint.

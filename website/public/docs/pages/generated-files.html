Project guide

Managed files & safety

Kite plans the complete generation before writing, records managed outputs, computes checksums, and asks before replacing conflicting files.

Project manifest

After initialization, Kite stores generation metadata in:

.kite/manifest.json

Each generation record includes the root template, template version, variables, generated paths, checksums, and upgrade policies.

Conflict strategies

StrategyCommandBehavior
AskDefaultPrompt before replacing an existing file.
Skip--skip-existingPreserve existing targets and continue with missing files.
Overwrite--forceReplace conflicts intentionally.
Preview--dry-runPrint the plan without writing files.

Recommended workflow

# 1. Preview
kite --feat:clean settings --dry-run

# 2. Generate while preserving existing shared foundations
kite --feat:clean settings --skip-existing

# 3. Analyze the result
flutter pub get
dart format .
flutter analyze

Why a feature may mention shared files

Root templates can require reusable foundations. For example, a clean feature may require Riverpod support, and the Dio preset requires both API contracts and Riverpod. Dependency resolution happens for each generation plan so missing requirements can be supplied automatically.

!
Repeated existing-file prompt

If your current Kite build asks about an already-created shared dependency while generating a new feature, use --skip-existing to preserve the project foundation. Do not use --force unless replacing those files is intentional.

Upgrade separately

kite upgrade --dry-run
kite upgrade

Upgrade commands are the appropriate place to compare template versions and refresh Kite-managed foundations. Manually changed files should be reviewed rather than replaced silently.

Feature architecture

MVC

Use Kite's feature-first MVC template for modules that benefit from a direct model, Riverpod controller, provider, and view structure without the additional data/domain boundaries of Clean Architecture.

Generate MVC

kite --feat:mvc dashboard

Canonical forms:

kite feature dashboard --architecture mvc
kite feature dashboard --mvc

Generated structure

lib/features/dashboard/ ├── controllers/ │ └── dashboard_controller.dart ├── models/ │ └── dashboard_model.dart ├── providers/ │ └── dashboard_providers.dart └── views/ ├── screens/ │ └── dashboard_screen.dart └── widgets/ └── dashboard_content.dart

Responsibilities

FolderResponsibility
models/Immutable feature state or serialized feature data.
controllers/Manual Riverpod Notifier logic and state transitions.
providers/Manually declared providers that expose controllers and dependencies.
views/Screens and feature-owned UI components.

Controller and provider

final class DashboardController extends Notifier<DashboardModel> {
  @override
  DashboardModel build() {
    return const DashboardModel();
  }
}

final dashboardControllerProvider =
    NotifierProvider<DashboardController, DashboardModel>(
  DashboardController.new,
);

Routing and serialization

# Generate and register a GoRouter route
kite --feat:mvc dashboard --route

# Use json_annotation/json_serializable for the model
kite --feat:mvc dashboard --json

# Combine both
kite feature dashboard --architecture mvc --route --json

When MVC fits

  • The feature has straightforward local or presentation-focused state.
  • The domain does not need reusable business contracts.
  • The team wants clear view/controller boundaries with less ceremony.
  • The feature can evolve into a richer architecture later if complexity grows.
!
Architecture should follow complexity

Use MVC because it fits the feature—not because every module must share the same folder count. Kite supports both styles so teams can make deliberate decisions.

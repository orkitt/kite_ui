Project guide

Extending Kite

Add new generators by composing registry entries, manifests, template source, supported command values, and generation tests. Shared contracts belong in internal dependency templates.

Add a component

Example: badge.

lib/src/templates/components/badge/ ├── manifest.json └── files/ └── kite_badge.dart.tmpl

Manifest

{
  "schemaVersion": 2,
  "id": "component.badge",
  "version": "1.0.0",
  "requires": ["component.foundation"],
  "dependencies": [],
  "devDependencies": [],
  "files": [
    {
      "template": "files/kite_badge.dart.tmpl",
      "target": "{{config.sourceDirectory}}/shared/components/kite_badge.dart",
      "upgradePolicy": "replace"
    }
  ]
}

Register and allow it

  1. Add component.badge to registry.json.
  2. Add badge to ComponentCommand._supported.
  3. Add generation and conflict tests.
  4. Run the template validator.

Add another architecture

Use an ID such as feature.mvvm, create features/mvvm/manifest.json, add the template files, register the descriptor, and allow mvvm in the feature command.

The generic shorthand normalizer can then translate:

kite --feat:mvvm dashboard

into:

kite feature dashboard --architecture mvvm

Add state or API presets

state.bloc

Create a public state preset and move reusable state contracts into internal templates where multiple presets need them.

api.http

Reuse api.core contracts while generating an alternative client implementation and provider wiring.

Design rules for templates

  • Generate compile-safe source.
  • Do not invent business operations.
  • Keep internal dependencies reusable and focused.
  • Use theme values instead of hardcoded UI colors.
  • Prefer manual Riverpod providers unless a template explicitly targets another state system.
  • Test multi-template bundles for target collisions.
